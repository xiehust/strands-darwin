# Optional AgentCore Memory

**English** · [简体中文](agentcore-memory.zh-CN.md) · [Guide index](README.md)

## What changes, and what does not

AgentCore Memory is **off by default**. Darwin's existing project-local `memory_recall`, `memory_save`, `/memory`, validation and retention remain unchanged. There is no migration or archive backfill. The model provider is independent: cloud memory does not switch your model or run a second model loop.

Enabling cloud memory adds gated project episode/reflection retrieval and host-configured preference retrieval. Uploading is a separate opt-in: manual preview/send or explicit project-scoped auto mode. A configured cloud preference is still untrusted contextual data, never an instruction with policy or permission precedence.

## Guided setup

Run `/setup-agentcore-memory` in the TUI. Darwin loads the complete [bundled setup guide](../../src/skills/builtin/setup-agentcore-memory/SKILL.md), then first inspects existing `~/.darwin/config.json` read-only through the ordinary permission gate. For enabled, valid memory config it runs offline `darwin doctor`, local-only `darwin cloud-memory status`, and a bounded live SDK read through `darwin cloud-memory preferences`, using saved settings. Empty records are success; results are reduced to success/count, not adopted or displayed as preference content. Even with `preferences: false`, this explicit health read is check-only. Upload off, explicit project scope and ignored legacy settings stay unchanged.

Healthy existing memory needs no repeat setup: Darwin reports region/actor/upload mode and local/read-only results, then stops without actor/default questions, config/resource edits or restart. This does not verify extraction, write/delete permission or strategy topology. Unrelated doctor warnings are reported separately, not used to reset memory. Denied/unreadable/invalid config or failed/unverified checks are blocked or pending repair, not absence; Darwin requests targeted confirmation and preserves known actors/resources. Only a genuinely missing or intentionally disabled configuration enters actor/default proposals; disabled is never silently enabled. Explicit reconfiguration requests preserve the original health result and require targeted confirmation of changes. Optional arguments and yolo mode are not mutation consent.

When setup or resource repair is needed, Darwin prefers a compatible resource you own. Otherwise it proposes an independent DarwinMemory resource, explains region/cost/retention, and asks for explicit confirmation before creation or config changes. Installation, IAM expansion, uploads, deletion and infrastructure import are not implicit. The guide's defaults include automatic project isolation, a bounded startup preference read, and manual upload staging—not sending. Existing values are shown and preserved unless you confirm a change.

This is model-driven guidance through ordinary permission-gated tools, not a deterministic provisioning wizard or a new sandbox. Expansion itself changes no config or cloud resource. The required built-in cannot be shadowed by project/global skills or custom commands; missing/corrupt guidance refuses startup. Activation failure restores the literal prompt and image plus later queued user entries to the editor, ahead of newer draft text, without sending them. Busy input queues until the next turn, and trajectory keeps the literal slash. The guide ships with installed Darwin; it does not depend on this repository's docs. It is the single source for exact namespace and request/config JSON templates.

TUI, development REPL, and text/structured headless modes use the same prompt expansion. `darwin -p "/setup-agentcore-memory"` loads the guide too. Healthy unchanged memory may finish without questions; setup/repair that needs input returns questions and pending status, never reads stdin or guesses. A successful question turn does not mean setup is complete. Restart only after a confirmed config change; the current runtime's tool catalogue is not refreshed in place.

## Provisioning and configuration

Resource setup is separate from the runtime data client. Use the bundled guide's exact episodic, reflection and user-preference templates, whether provisioning manually or through confirmed guided setup.

Declare the custom lowercase `projectid` in the resource's `namespaceKeys`. Every uploaded event supplies `extractionConfig.namespaceVariables.projectid`, with a lowercase value. Missing variables can allow CreateEvent to succeed while extraction is skipped: monitor AWS extraction logs/`NamespaceResolutionFailure`. Do not provision a broader reflection namespace; validating returned namespace labels cannot undo cross-user synthesis performed by a wrongly configured strategy. IAM must restrict the resource and appropriate operations (`RetrieveMemoryRecords`, `GetMemoryRecord`; `CreateEvent` only for uploads, `DeleteMemoryRecord` only for explicit deletion). Configure the resource's event expiry deliberately; it is not long-term record retention.

Runtime access uses the official `@aws-sdk/client-bedrock-agentcore` **3.1127.0** package (Node >=20, within Darwin's supported Node range). It includes CreateEvent `extractionConfig.namespaceVariables`; no AWS CLI executable or capability subprocess is needed. Darwin uses the standard SDK credential chain, including environment, profiles, container credentials and instance roles, and respects `AWS_EC2_METADATA_DISABLED`. It neither changes credentials nor derives actor identity from them. The AgentCore region is explicit; SDK `ignoreConfiguredEndpointUrls: true` excludes environment/shared-config service endpoint URLs without changing process environment. Credential services use an independent SDK handler, not the per-memory abort/JSON guard. The standard `role_arn`/`source_profile` AssumeRole chain is covered by a local STS XML/signing fixture; nested credential clients also exclude configured service endpoint URLs and use one attempt. Credential-service regions still follow the standard profile/SSO selection. This does not disable credential sources such as container credential URIs, instance metadata, SSO, or user-configured credential processes; those remain trusted user credential configuration, not model inputs. Get/Delete forward the fixed preference namespace for IAM condition authorization, in addition to local scope validation.

**Existing config:** after confirmation, remove only `agentCoreMemory.cliPath`. A legacy absolute string up to 1024 characters is still validated and accepted, but ignored with a bounded migration notice; it is never executed or printed. Preserve region, resource/strategy IDs, actor, automatic project identity (omit `projectId`), `preferences: true`, and your existing `upload: manual` choice. The runtime does not automatically rewrite configuration, approvals, namespaces or outboxes. New unknown keys remain errors. **Some existing preference approvals need re-review:** metadata timestamps formerly formatted by CLI as `2026-01-01T00:00:00+00:00` become SDK ISO `2026-01-01T00:00:00.000Z`. Metadata bytes participate in the evidence hash, so even a format-only difference withholds that preference. After local approval checks, status reports changed approvals and asks for `/cloud-memory inspect <record-id>`, then confirmation of the displayed hash. The old proof is never silently rewritten; byte-identical proofs still apply.

The optional [`agentcore` infrastructure CLI](../architecture/agentcore-cli-memory-plan.md) is a separate lifecycle tool, not a runtime dependency. Keep the existing resource: the verified CLI schema drops `namespaceKeys`, and import filters templates containing `{memoryStrategyId}`. Resource import/deployment remains deferred until a lossless migration is separately verified and authorized.

The [bundled guide's configuration section](../../src/skills/builtin/setup-agentcore-memory/SKILL.md#4-apply-only-the-approved-configuration) contains the canonical root `agentCoreMemory` JSON. Merge only confirmed fields into private `~/.darwin/config.json`, preserve all unrelated settings, and keep mode `0600`; never store credentials or commit the config. `trajectory: false` requires a decision before manual upload can be enabled.

Use actual IDs; placeholders are not resources. `actorId` is your configured stable opaque user ID, shared across projects, never email or AWS credential identity. `projectId` is independent; omit it for a SHA-256 key of Darwin's canonical project key. An explicit project ID lets separate checkouts deliberately share project episodes. Actor/strategy IDs accept alphanumeric, `_`, `-` segments up to 128 characters; project ID is lowercase and at most 64 characters (the service namespace-value limit). Region is explicit. Unknown fields and traversal-like scope strings are refused. `timeoutMs` is 100–15000, default 5000; `preferences` defaults true *inside enabled config*; `upload` is `off` (default), `manual`, or project-authorized `auto`. Uploads require trajectory enabled; root auto alone fails closed. See [project overrides](configuration.md#project-overrides) for identity derivation, precedence and budget configuration. Omit `agentCoreMemory` or set it to `false` to disable: no cloud controller, tools, network, or cloud-state writes.

See AWS's [namespace organization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/specify-long-term-memory-organization.html), [episodic strategy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/episodic-memory-strategy.html), and [CreateEvent](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/short-term-create-event.html) documentation.

## Recall and preference adoption

The parent model gets `episodic_recall({intent, limit?})` and `reflection_recall({useCase, limit?})`. Query length is 1–300 characters, limit 1–5 (default 3); secret-like queries are refused. Intent should describe the task goal; useCase should describe applicability/context. Both use `RetrieveMemoryRecords.searchCriteria.searchQuery` and the configured strategy ID. They are external network calls, not statically safe local memory: ordinary hooks, plan mode and deny rules run before the SDK request. Children do not receive either tool. Startup preference retrieval is different: enabling `preferences` explicitly authorizes that bounded host behavior, including in plan mode.

`namespacePath` is hierarchical. Darwin first validates **every** returned namespace, strategy and bounded metadata value against the actor/project/resource binding. Wrong-scope records fail the whole response closed. In-scope episodes returned alongside reflections are omitted with explicit omission/underfill reporting; retrieval never broadens to compensate. No invented AWS type filter is used. Episode/reflection XML is projected into an ordered tree; evidence, assessment and action order remain data. Attributes, DTDs, processing instructions, unknown entities, malformed or oversized XML are refused. Reflection confidence estimates usefulness, not probability of correctness. A schema variation may be refused rather than guessed.

Imagine a retrieved record says “the user explicitly prefers concise answers.” That generated claim is not proof. Darwin does not automatically apply it. Use:

```text
/cloud-memory preferences
/cloud-memory inspect <record-id>
/cloud-memory confirm <record-id> <displayed-hash> global
/cloud-memory forget <record-id>
/cloud-memory delete <record-id> cloud
```

Inspect shows the complete bounded preference and hash. Confirm is your explicit adoption of that visible content as an enduring **cross-project communication/collaboration preference**. Do not confirm implicit guesses, one-time requests, project constraints or policy instructions. Approval binds region/resource/actor/strategy/namespace/record/content; changed content requires fresh inspection and approval. No unsupported citation/proof fields are invented. Once before the first model request in each runtime, a bounded general-preference search caches at most five candidates. Later requests (including compaction) reread local approvals/revocations without cloud retrieval. Explicit `preferences` refreshes the cache; `inspect` updates that record. Remote edits are detected on refresh or a new session, not by server push. A denied PreCompact hook runs before any cloud retrieval. Retrieval failure or unavailable proof applies nothing. Compact and multiline JSON objects or bounded arrays of `{context, preference, categories}` are validated and preserved literally, with optional `language`: [AWS extraction uses arrays while consolidation stores single objects](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-user-prompt.html). The original bytes determine the approval hash; generated `context` is not evidence of a user quote. Inspection and approval are separate files, so a concurrent inspect cannot restore forgotten approval. Local forgetting removes approval immediately, including before the next invocation in another active project. It does not erase historical assistant replies or cloud data. Delete is separate, explicit, scope-checked and irreversible remotely; source events may regenerate records, which remain unapproved. Correction means forget, inspect the corrected cloud record, and confirm its new hash.

## Review and send new turns

Set `upload: "manual"`, then work normally. Only newly closed durable trajectory turns become candidates. Darwin does not await AWS while streaming. Failed, cancelled and incomplete turns keep their actual outcome; `endTurn` is not task success. Nothing is sent yet:

```text
/cloud-memory pending
/cloud-memory preview <token>
/cloud-memory send <token> <preview-hash>
```

Preview displays the exact CreateEvent body, scope, source session/turn/ordering, quality facts and hash. **This can include secrets and is not a confidentiality guarantee.** Future turns retain bounded original textual content from every tool kind, including arbitrary MCP tools, subagent reports and public memory tool results. There is no tool-name whitelist or sensitive-word/path filter. Newlines, slash commands, markup, paths and token-like strings remain literal. `USER` carries the actual submitted goal; each `TOOL` carries one invocation identity plus its input and corresponding result; `OTHER` carries provenance, closing outcome and omissions. SDK status and structured bash exitCode are separate facts, so status success with exitCode 1 remains a failed command. A missing result is stated, never fabricated. No task-success claim is inferred.

All assistant prose/reasoning and binary/image blocks remain excluded. The collector does not traverse child conversations, read files named by tools, or hydrate offloads/archives. Tool text can itself contain file contents, diffs, logs, skills or memory; those public results are now eligible. Original SDK execution evidence is observed synchronously before after-tool hooks, trajectory truncation and result offloading; later output interventions may change what the model sees. An available public result from batch cancellation, executor failure or background dispatch is captured as a labelled fallback only when no execution snapshot exists. A dispatch acknowledgement is kept separately and never implies task completion. If the originating turn remains open, its final result is added there. Otherwise the next ordinary turn receiving the existing parent background event includes an explicit late TOOL record referencing the original turn and invocation; the sealed old candidate never changes, and no synthetic USER goal or new wake/upload channel is created. Between turns, at most 64 copied origins and 16 bounded result bodies are retained; capacity/cancellation losses are counted in status. Cancellation drops pending background correlation and shutdown closes the collector. Evicted action summaries still receive observed status/exitCode/failure, with failure text recovered when possible and missing input labelled. Ordinary textual JSON is not discarded merely because its `type` is `image` or `audio`. Invocation-state identity isolates results; reused IDs within one state are marked ambiguous rather than guessed. Short input/results share the full serialized 8 KiB action budget, including metadata and escaping. Long collections retain bounded prefix/suffix entries with exact indices, and large stdout does not consume the space needed by known short stderr/metadata fields. Only durable turn settlement schedules detached local file work. No observer performs I/O or network calls; no model summarizer or extra model calls are used. Existing entries, proofs and tokens are never regenerated or backfilled. Decline with `/cloud-memory discard <token>` to remove a pending body and unblock later turns; leaving it pending preserves the ordering block. In manual mode no background sender decides for you.

Manual send requires a prior preview of the unchanged bytes. Events preserve Darwin session ID, turn/sequence order and a stable idempotency token; later turns wait for earlier pending turns in the same session. There are at most three attempts per event; manual retries are explicitly requested. Restart does not resubmit accepted events. A lost acknowledgement can leave a pending event that AWS already accepted; retry uses the identical token/body. “AWS event accepted” never means “episode generated.” Extraction and reflection happen asynchronously, and incomplete episodes may not appear yet.

Standalone `darwin cloud-memory` is read-only: `status`, `preferences`, `inspect`, `pending`, `preview`. Inspect/preview write no approval or preview proof. Failures, invalid usage and cancellation exit nonzero; disabled status exits zero. Headless mutation is unavailable in this first version (including the development REPL). Only actual user-submitted TUI `/cloud-memory` management can confirm, forget, delete, send, discard or clear accepted bodies. A hash binds reviewed bytes; it is not proof that a human authorized them. This closes the ordinary model-bash CLI route, including broad allow-rules. It is not a shell sandbox: explicitly approved arbitrary shell, a pseudo-terminal driver, direct AWS CLI, or code/filesystem access under the user's credentials can still act outside this command boundary. `/cloud-memory`, `/status`, startup and post-turn notices report enabled/degraded state; the live frame gains no rows. Busy TUI management is refused rather than queued.

## Project-scoped automatic upload

At idle, type `/cloud-memory auto` yourself to persist this project's consent, or `/cloud-memory manual` to stop unsent automatic work immediately. Neither command invokes a model, adopts preferences, deletes cloud data, resets the conversation, nor sends existing pending entries. Content may include secrets. Global config holds a strictly validated `projectOverrides` map; [identity and precedence](configuration.md#project-overrides) are shared by TUI, CLI, doctor, model switches and successors. Auto consent v2 binds a fresh epoch to the canonical working-tree key as well as the unchanged cloud scope. Sharing an explicit cloud `projectId` shares namespace/quota, never consent. Old v1 authorizations stay inactive until user reconfirmation; pending/manual bodies and hashes are unchanged. Do not manufacture authorization JSON through a model tool.

Only new immutable `darwin-upload-v2` bodies with separately persisted provenance from that epoch qualify, after durable turn close and event-file publication. Failed tool outcomes are valuable: a normally closed `endTurn` is eligible, not evidence of task success. Cancelled, incomplete, provider-failed, ambiguous or seriously damaged collections are held for manual review. A traceable action/result and goal (or genuine late result with original identity) are required; metadata/acknowledgement-only turns are not sent. Normal bounded truncation is allowed. No sensitivity whitelist, omitted-percentage veto, archive scan, resume-pointer scan or retroactive enablement exists.

Default UTC-day quota is **500 attempts / 104857600 bytes (100 MiB)**; root defaults and project overrides can raise it within validated bounds. A reservation counts one attempt and the exact serialized HTTP request-body bytes, not a unique event or extracted memory. It is durable before launch, shared across processes/restarts (including checkouts sharing explicit project identity; ledger at `~/.darwin/agentcore/auto-quota/<project-id>/usage.json`) and conservatively consumed even if cancelled or the acknowledgement is unknown. Retries keep the same token/body: at most three total, with cancellable 250/500 ms backoffs for network failures, 429 and 5xx. IAM/configuration 4xx and other permanent transport failures stop that authorization visibly until repair and fresh consent. After credentials/signing, stop-file reads and reservations, a short shared config lock covers a fresh policy read, validation and synchronous HTTP-handler invocation. Native manual publication and launch are ordered by that lock; a completed revocation prevents later launches. The lock is released before waiting for the response, and competing commands fail promptly rather than waiting for network I/O. Already-issued effects cannot be undone; received acknowledgements remain durable.

Sending runs outside the turn/observer, serially under the existing outbox lock. An activity-owned pass tries at most eight candidates; publications during a pass coalesce into a followup pass. Same-process sessions queue behind the active sender without losing their publication trigger; cross-process contention still refuses through the outbox lock and needs later ordinary activity. Held/budget/order states never schedule themselves. Held earlier entries block their session until explicit manual send/discard, not unrelated sessions. Budget-paused entries remain inspectable and resume on later ordinary activity under the same authorization. Existing enabled controllers reread local policy at new-turn, model-switch, clear/rewind and status boundaries, including manual/off controllers with no prior override. Only new turns can capture new consent; malformed policy fails closed without failing the ordinary turn. Fully disabled runtimes remain controller-free. There is no timer daemon, hidden model turn or new live TUI row. Shutdown/cancel/clear cancel owned sends and bound local drain to two seconds; shutdown does not guarantee every queued item is sent. Accepted events are not proof of extraction.

Only **auto-accepted local bodies** may expire after seven days, during later authorized activity. Pending/manual/failure bodies and cloud records never expire automatically. A durable per-token receipt precedes removal and survives it permanently; no old 256-receipt eviction occurs. Limits are 4096 bodies, 512 pending, 32768 outbox entries, and 4096 receipts per hash-prefix partition. These bounds fit seven days at default throughput; larger quotas can reach capacity sooner and pause/omit visibly rather than lose existing data. `/cloud-memory pending` lists at most 64 bodies and states omissions; `/cloud-memory` and `/status` expose policy, budget usage, queued/held/paused state and failures.

### Batch legacy cleanup

`/cloud-memory discard-legacy` previews at most 256 current-project/current-binding unaccepted non-v2 events, with count and bounded identifiers. Only `/cloud-memory discard-legacy <manifest-hash>` confirms that exact locked manifest. A changed manifest refuses before removal. Tombstones are durable before any body/proof deletion; repeating the confirmed hash completes interrupted cleanup. Accepted events, v2, foreign directories, preferences, trajectory and cloud records are untouched. CLI mutation remains refused. This is a capability: no real legacy cleanup was performed while implementing it.

## Bounds, lifecycle and verification

Transport: four official AWS SDK Commands, no shell, executable, stdin or temporary request file. Serialized CreateEvent upload bodies are at most **256 KiB**, including JSON escaping; other request inputs remain at most **32,000 UTF-8 bytes**. Upload payloads have at most 100 messages and each message is at most 100,000 UTF-8 bytes. A supported HTTP-handler extension limits successful response bodies to **256 KiB** and error bodies to **8 KiB** before collecting/parsing them; successful JSON also has finite depth/count checks before SDK deserialization. SDK Dates become ISO strings; only top-level SDK `$metadata` is removed, never memory metadata. Unknown response fields are refused rather than silently lost through SDK decoding, with one exact exception: RetrieveMemoryRecords may include a top-level `searchType` hint not modeled by the pinned SDK. It must be a nonempty control-free string of at most 64 UTF-16 code units and is omitted before record checks. No other operation or nested field is exempt; record/XML validation remains strict.

`maxAttempts: 1` leaves retries to the shared outbox sender. One total timeout covers credential resolution, signing, connection and response consumption. Cancel/timeout returns even if a credential provider is still waiting; a final handler guard prevents that provider's later completion from sending a request. Already-issued effects cannot be undone. Cancellation is per controller; shutdown destroys its SDK client and sockets. Service diagnostics, credentials and request IDs are omitted; bounded HTTP status may be shown. No transport files are created or cleaned up. Existing durable outboxes and state files remain private plaintext, not encrypted or securely erased.

Retrieval returns at most five records, each at most 12,000 characters; XML caps at 500 tokens and 16 levels. No pagination/archive download. Approvals: 64 local records with separate inspection/adoption files, at most five applied with 4,000 characters of validated JSON each. Outbox: 4096 bodies (at most 512 unaccepted) per configuration/project binding, eight queued local jobs, 32768 directory entries. A full outbox visibly omits new candidates without evicting existing data. Only event files have the larger 257 KiB state cap (256 KiB request plus envelope); preference proofs, receipts and other state keep 64 KiB. Collection holds at most eight transient turns, each with 64 full actions (at most 8 KiB each), 96 lightweight omitted-action summaries and an 8 KiB goal. Collector-turn and detached-job queue omissions have separate counters and reasons in status. The newest 16 operations are favored, then failed actions and immediate recovery, before exploratory history; selected pairs are rendered chronologically. Content truncation, action-capacity omission, missing/unmatched results and excluded internal events are distinct quality facts in preview/pending. Empty goal-free/action-free turns produce no entry.

Long text keeps exact Unicode-safe head/tail segments (roughly one-third/two-thirds), with byte lengths and UTF-16 source ranges outside the original text. For strings beyond the bounded 262,144-unit scan, original byte length is explicitly unknown rather than scanning unbounded data; retained bytes/ranges and original UTF-16 length are exact. JSON traversal stops at depth 8, 128 visited values and 32 entries per container; omitted regions are marked, with four detailed loss records plus an aggregate. Existing upstream truncation/offload notices remain source limitations, never silently hydrated. Unmarked upstream loss may be undetectable. Full/degraded queues state the omission; no eviction or silent deletion. `/cloud-memory clear-accepted` explicitly removes accepted bodies and attempt/preview files to free body capacity. Discard and cleanup first persist a receipt/tombstone; cleaned tokens cannot upload again. Existing 256-token receipt ledgers remain readable and unchanged. New receipts use per-token files in 256 hash-prefix partitions, each capped at 4096 files. Lookup reads only the token and legacy ledger; partition capacity is checked before send/removal. No receipt is evicted; a full partition pauses visibly. Ordering remains among non-discarded pending turns. Send/discard/cleanup use an exclusive cross-process lock and refuse in-flight work; a crash-held `active.json` (also used for bounded preference-state writes) requires manual owner inspection/recovery, never automatic lock stealing. New state is written and synced privately, then atomically published without clobbering. Interrupted `.tmp` files are not events/attempts and are never silently deleted by a later run; directory capacity still counts them. Legacy corrupt final entries need manual review rather than guessing order. Old OTHER-only payloads remain previewable/discardable but cannot upload or be automatically converted. Interrupted cleanup is reported and can be completed by repeating the user command from its receipt/tombstone.

Approvals live under `~/.darwin/agentcore/<binding>/`; outboxes under `~/.darwin/projects/<project-key>/agentcore/<binding>/<scope-binding>/`. These are sensitive user-owned policy paths. Files are private and symlinks refused. Disabled mode does not touch them. `/clear` and `/rewind` create fresh session controllers and refresh preferences, keep durable outboxes, and do not undo AWS effects. Cancellation is per management operation and bars later state publication/SDK requests, even after disk awaits; a fresh command after Esc remains usable. Already-issued effects are not undone, and received AWS acknowledgements are retained. Cloud-controller shutdown cancels and drains management plus local projection work for at most two seconds; on timeout it reports outstanding filesystem work, whose cancelled mutations remain barred (a lock may persist until that I/O returns). Runtime send/compact also recheck cancellation after local preference preparation, before invocation, without refetching the cache. A crash before the detached local projection is persisted can omit that candidate; there is deliberately no archive repair/backfill. Raw-event expiry/deletion does **not** delete long-term records.
