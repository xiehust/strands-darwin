### F1 — The terminal-delivery ledger reads the offloader's replacement, so every offloaded terminal `wait` still wakes

**The Host's hypothesis is confirmed**, by the record, by the source, and by running the repository's own parser.

- **Evidence (record):** Nine `wait` calls returned `reason: "terminal"` in completed turn 1. The six whose results stayed a single `json` block (seq 62, 171, 186, 203, 357, 451) produced no wake. The three whose results were replaced by a single text block beginning `[Offloaded: 1 blocks, ~N tokens]` each produced exactly one wake:
  - seq 131 (`bg-5eb18a7d…`, ~9,481 tokens) → wake seq 483;
  - seq 329 (`bg-8ebc3cbf…`, ~5,282 tokens) → wake seq 489;
  - seq 425 (`bg-5ef1fbc0…`, ~5,420 tokens) → wake seq 495.

  The correlation is 3/3 offloaded→wake and 0/6 non-offloaded→wake. There were no other wakes.
- **Evidence (source):**
  - `ContextOffloader` registers `agent.addHook(AfterToolCallEvent, e => this._handleToolResult(e))` at the default order (`HookOrder.DEFAULT` = 0). For an over-threshold result it assigns `event.result = replacement`, a `ToolResultBlock` whose content is one `TextBlock` of preview text (`vended-plugins/context-offloader/plugin.js`, `_offloadToolResult` / `_handleToolResult`).
  - The stream then yields that mutated `afterToolCallEvent`. `AgentRuntime.send` passes it to `this.terminalDelivery.observe(event)` at the same point `recordStream` records it, which is why the trajectory shows the preview.
  - In `src/agent/task-terminal-delivery.ts`, `resultPayload` accepts one `jsonBlock`, or one `textBlock` that `JSON.parse`s. A preview beginning `[Offloaded:` parses to nothing, so `terminalTaskIdsInToolResult` returns `[]` and nothing enters `pending`.
  - At drain time `has(taskId)` is false and the wake is sent. The "Background-task wake" section of `docs/architecture/load-bearing-decisions.md` promises suppression for any terminal `wait`/`status`/`stop`/`list` result in a completed turn. "Durable context offload" says main runtimes offload by default, and neither section mentions the other.
- **Evidence (executed):** `terminalTaskIdsInToolResult('bash', …)` was imported from the repository and run on each stored original in `offload/offloader/<toolUseId>_0`, and on each recorded preview. For all three stored originals it returns the task id; for all three previews it returns `[]`.
- **Refinement of the hypothesis:** the model *did* see the terminal fact. Every preview begins `{ "reason": "terminal", "output": { "taskId": "bg-…"`, because `finishTerminalWait` sets `reason: 'terminal'` only when `status.state !== 'running'`. So suppression would have been semantically correct: this is a missed observation, not a correct refusal.
- **Ruled out:** the seq 50 offload was a foreground `execute` result, which never carries task state, so it is irrelevant. SRF-033's `$value` fix (`48c1b8c`) does not touch this path.
- **Root-cause area:** context management (a hook-order interaction between two load-bearing decisions).
- **Suggestion:** feed the ledger the pre-offload result. Register a parent-runtime `AfterToolCallEvent` hook at `HookOrder.SDK_FIRST`, the same precedent as the cloud-memory `uploadObserver.after`, which is documented there as "pre-after-hook execution evidence". It runs before the offloader and records candidate terminal ids from the original result, keyed by `toolUseId`. When the yielded event's content differs from the captured original (the result was replaced), commit a candidate id only if the model-visible replacement text contains that exact task id. That keeps "the model saw it" conservative for offloaded `list`/`status` results whose later snapshots fell outside the preview. Pending/commit-on-`endTurn` stays unchanged, as does observer discipline (synchronous, non-throwing). Do not add `bash` to `excludeTools` or parse preview prose for state.
