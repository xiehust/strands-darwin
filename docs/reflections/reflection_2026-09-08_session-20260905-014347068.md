### F1 — A child's stream interruption is terminal for the child; the parent's one-shot continuation does not reach `subagent` children

- **Evidence:** Turn 1's parent stream died at seq 31 and darwin continued it as turn 2 at
  seq 32 (49 ms later) — the SRF-001 path. In turn 26 the same exact `ModelError` killed two
  children (seq 1741 after 11 m 46 s, seq 1761 after 9 m 24 s) and each surfaced to the parent
  as the bare `Error: Stream ended without completing a message`: no SER-063 last-text tail
  (the last completed assistant message in each child was a tool-use-only message, so there was
  no text to carry) and no SER-075 `continue` (a failed child is retained only when its
  conversation ends in a complete assistant message; these ended in a tool result). The parent
  had to re-derive the child's progress from disk (seq 1745–1757, "The child got through the
  captions refactor before its stream was cut off"), re-dispatch once, then abandon delegation
  and write the 23-slide script itself in bounded pieces (seq 1781–1806). 21 m 10 s — 61 % of
  the session's longest turn — bought nothing.
- **Root-cause area:** orchestration.
- **Suggestion:** In `SubagentTool` (`src/agents/subagent-tool.ts`, the `child.invoke(...)`
  call inside `dispatch`), when `invoke()` rejects with `isRetryableStreamInterruption(error)`
  from `src/agent/stream-resumption.ts` and `child.cancelSignal` is not aborted, run exactly one
  `child.invoke(STREAM_CONTINUATION_PROMPT, { invocationState })` on the same live child —
  its conversation is intact in memory (the SDK never stores the message whose stream failed,
  so the history ends at the last tool result and a user-role continuation is a legal next
  message). Publish a `continuing-after-stream-interruption` safe phase on the dispatch
  heartbeat through the existing `setPhase`, count it once per dispatch, and if the continuation
  also throws rethrow through `withFailedChildText` with the *original* error preserved as
  `cause` (so the retry guard and `turnEnded.failure` see the same class). Never inside the SDK
  loop, never a second attempt, never for cancellation; `workflow` Graph nodes are out of scope
  for this direction and the tool description should say the child is continued once.

### F2 — `/compact` leaves no trace in the trajectory, and the first `modelCall.contextTokens` after it is stale

- **Evidence:** seq 1245 (turn 15 `turnEnded`, 07:03:52) is followed by seq 1246 (turn 16
  `userInput`, 07:39:55) with nothing between them; seq 1250 records `contextTokens: 705408`
  for a call whose own spend is input 4 + cacheRead 0 + cacheWrite 43,990 (≈ 44k real prompt
  tokens, and a full cache miss); seq 1255 then records `contextTokens: 46647`. A 15× shrink of
  a running session's history can only be the summarizing conversation manager (`/compact`,
  config `summaryRatio 0.8, preserveRecentMessages 10`), yet a reader — `trajectory replay`,
  `/export`, or this reflection — has to infer it. The stale number is the SDK's
  `_estimateInputTokens` baseline: it takes the last assistant message that carries usage
  metadata, and after summarization a preserved recent message still carries its pre-compaction
  usage until the next completed call.
- **Root-cause area:** context management / other (trajectory legibility).
- **Suggestion:** Add one bounded observer record type `contextCompacted` (alongside
  `shellCommand` and `taskNotification`) written by the TUI driver after a successful
  `AgentRuntime.compact()`: `{ before: { messages, estimatedTokens? }, after: { messages },
  focused: boolean }` — counts only, never the summary text or the focus. `trajectory replay`
  and therefore `/export` print one line for it (`context compacted: 214 → 12 messages`), and
  `spend.ts` treats the first `modelCall` after it as an anchor drop when printing
  `context ~N tokens`. No SDK change; `contextTokens` semantics stay documented as "the SDK's
  pre-call projection".

### F3 — A rewind successor's `runStarted` cannot say where its 188 messages came from

- **Evidence:** seq 0 `resumed: false, restoredMessages: 188`; seq 5 (first call) spends
  cacheWrite 240,978 with cacheRead 0 on a 239,287-token context. `startRewind` creates the
  successor with `session: { kind: 'new' }` and `rewindRestore: { sourceSessionId, snapshotId }`,
  but `runStarted` is composed from `session.restoreRequested` and `agent.messages.length` only,
  so the record reads as a fresh session that somehow began with 188 messages. The predecessor
  `session-20260904-145930073` holds one checkpoint (completed 2026-09-04T15:18:44Z) that fits.
- **Root-cause area:** other (trajectory provenance).
- **Suggestion:** When `options.rewindRestore` is set in `AgentRuntime.create`, add an optional
  `rewindFrom: { session, snapshotId }` field to the `runStarted` record (`src/agent/runtime.ts`
  writer options, `src/trajectory/record.ts` reader/normalizer), and print it on the
  `trajectory replay` header and the resume recap (`resume recap · … · rewound from
  session-… snapshot …`). Additive, bounded strings, no change to `resumed` semantics.
