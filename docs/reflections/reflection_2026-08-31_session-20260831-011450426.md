## 4. Improvement findings for darwin

### F1 — `memory_save`'s input schema trims the evidence quote, so indented source lines can never validate, and the error hides the real reason

- **Evidence:** seq 347→348: the agent sent `evidence.quote = "    \"swebench>=4.1.0,<5\","` — verified byte-identical to line 11 of `adapters/darwin-swe-bench/pyproject.toml` inside the session (`cat -A`, seq 351–352) and again during this reflection — and was rejected with "memory evidence must be one unique exact current project line". Root cause is in darwin's code, not the record: `src/memory/tools.ts:10` applies `z.string().trim()` to every bounded field including `evidence.quote`, while `resolveExactSourceAnchor` (`src/memory/validation.ts:73`) requires the quote to equal a full file line (`line === evidence`). The trim strips the 4-space indentation, so the controller compared the *unindented* string and correctly found no whole-line match — reproduced during this reflection: `resolveExactSourceAnchor` with the untrimmed quote returns a valid anchor against today's identical file, with the trimmed quote returns none. Consequence in the record: two failed calls (seq 343/345, 347/348), ~2 minutes and 3 model calls of phantom-chasing (seq 351–355), a lost durable memory, and a wrong hypothesis ("untracked in git") delivered to the user (seq 355).
- **Root-cause area:** other (tool input schema bug) + tool description/error text
- **Suggestion:** stop trimming quote fields — give `evidence.quote` (and `userQuote`, whose `uniqueOccurrences` check has the same corruption exposure) a bounded-but-untrimmed schema so the controller sees the caller's exact bytes; and make the rejection reason-specific (no-such-line vs. multiple-matches vs. unreadable-file), so an exact-evidence failure is diagnosable instead of gaslighting the agent that just verified its quote with `cat -A`.

### F2 — `fileEditor create` refuses existing scaffold files with a dead-end error, and the model repeated the mistake

- **Evidence:** seq 162→163 and seq 227→228: two `create` calls on files the `harbor adapter init` scaffold already contained, both refused with "File already exists … Cannot overwrite files using command `create`.". The agent recovered each time by `rm` then re-create (seq 165/169, 230/233), costing roughly one model-call round-trip (~1 minute at this session's cadence) per miss; the second miss shows the first error message did not teach the recovery.
- **Root-cause area:** tool description / execution time
- **Suggestion:** extend the pinned SDK fileEditor patch (the same seam as the existing exact-`str_replace`-miss advisory) so the create-refusal error appends the recovery options — view + `str_replace` to keep history, or delete first for a full rewrite — turning the second occurrence's wasted round-trip into a single self-correcting step.
