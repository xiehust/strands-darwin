## 4. Improvement findings for darwin

### F1 — Successful bash list results fail to suppress already-delivered task wakes

- **Evidence:** Turn 2's cancellation (seq 625) legitimately discards pending delivery credit. However, turn 4 / seq 635 then returns ten stopped jobs and the running replacement as `json: {"$value": [...]}`, followed by a successful endTurn at seq 640. Eight already-listed stopped jobs still generate turns 5–12 / seq 641–682, despite repeated “no action needed” replies. Those eight turns use 1,645,703 cache-read tokens for 1,180 output tokens.
- **Root-cause area:** Orchestration / token spend. `src/tools/background-bash.ts:809–810` returns `manager.list()`. The installed SDK's `function-tool.js:220–238` wraps ordinary arrays in a `$value` object. `terminalTaskIdsInToolResult` in `src/agent/task-terminal-delivery.ts:59–77` handles bare arrays and direct/wait snapshots, not this envelope. This is a concrete result-shape mismatch, not evidence that cancellation should commit pending delivery. The load-bearing background-wake section explicitly promises suppression after completed `list` delivery.
- **Suggestion:** Extend only the ledger's pure payload decoder to accept the SDK's exact array envelope for successful bash results, apply the existing terminal-id/state validation to its elements, and keep endTurn-only commit. Add real SDK tool-stream and real pty coverage proving that a completed list suppresses queued terminal jobs while running, malformed, failed, cancelled and unrelated-tool results do not. Do not coalesce notifications, alter FIFO, change cancellation semantics or fork the SDK loop.

### F2 — Numeric summaries need executable reconciliation before confident attribution

- **Evidence:** Turn 15 / seq 750–751 aggregates requested quantities where executed quantities are absent; the implied position fails to match turn 13 / seq 708. The final table at turn 15 / seq 753 misses its own total by 100 after its stated residual, and advances uncomputed counterfactual interest/rank claims. The official aggregate values at seq 744 remain usable; uncertainty belongs in the detailed breakdown, not in invented precision.
- **Root-cause area:** System prompt / answer verification. `DEFAULT_SYSTEM_PROMPT` currently requires running verification for changes but has no equivalent numeric-report contract (`src/agent/system-prompt.ts:60–64,83–84`). This does not establish that prompt wording alone guarantees mathematical correctness; it identifies a small missing instruction at an existing seam.
- **Suggestion:** Extend the existing verification rule with a concise domain-neutral instruction: compute material reported totals with an available local tool, reconcile them to the authoritative aggregate and units/time window, distinguish requested from executed quantities and observed from counterfactual values, and report any unverified component or residual explicitly instead of claiming a full reconciliation. Preserve base-prompt override precedence, composition, tool catalogue absence and driver behavior. Test the exact default contract and unchanged override/composition paths; do not add a financial calculator tool or second model pass.

### F3 — Generated autonomous loops need the same bounded retry discipline as tool calls

- **Evidence:** Eleven same-class HTTP 400 concentration failures are embedded in one successful wait (turn 2 / seq 388), before stopping and repairing the bot at seq 397–410. A distinct 409 capacity condition is explicitly retryable (seq 236, 258); uncertain POST completion appears in seq 544, after a client repair to avoid blindly replaying writes (seq 442). Treating all three cases alike is unsafe.
- **Root-cause area:** System prompt / generated automation. The runtime retry guard counts SDK tool results, not iterations inside user-code processes; the existing default rule speaks only of a tool failing (`src/agent/system-prompt.ts:62–64`). Moving an unbounded loop into a successful long-running bash job escapes that behavioral guidance without violating the runtime guard's deliberate boundary.
- **Suggestion:** Add a concise generated-automation clause beside the retry rule: scripts with side effects must bound repeated deterministic rejection attempts, emit a reason and pause the affected action for changed inputs or observed state; retryable capacity/rate limits need bounded backoff honoring server guidance; ambiguous write outcomes require reconciliation or idempotency before replay. Require offline representative response-sequence checks before unattended launch when feasible. Keep this a code-generation instruction, not a runtime parser of arbitrary logs, and do not impose a new permission policy or trading-specific logic.

### F4 — Runtime interpretation of arbitrary application logs would be an unsafe shortcut

- **Evidence:** The failures at turn 2 / seq 388 and 544–593 are text inside successful bash results, while `400`, `409` and `429` also occur in the legitimately read API documentation (seq 75, 83). Seq 593 includes an older timestamp from a restarted process. The record therefore supports a visibility gap, but not a safe universal interpretation of log vocabulary.
- **Root-cause area:** Orchestration / tool-result classification.
- **Suggestion:** Consider a generic runtime log interpreter that promotes embedded HTTP error text to retry-guard failures and stops a background process after repeated matches. **Reject this implementation direction:** arbitrary logs are not an execution protocol, historical/documentation text can match, and forcibly stopping a process may interrupt successful side effects. F3 addresses generated code at its source without this unsafe cross-layer inference.
