## 4. Improvement findings for darwin

### F1 — Root cause of the unanswered question: Bedrock's `contentFiltered` stop is a model refusal darwin does not recognise, so the turn ended silently

- **Evidence:** All three final model calls stopped with `stopReason: contentFiltered` (seq 2079,
  2084, 2089); the `agentResultEvent`s carry the same stop reason (seq 2080, 2085, 2090) and the
  `turnEnded` records close normally with no `failure` (seq 2081, 2086, 2091). The Bedrock model
  card for Claude Fable 5.1 states the model "includes blocking classifiers for dual-use content in
  cybersecurity and life sciences", that a block returns HTTP 200 with `stop_reason: "refusal"`,
  that "refusal rates on this model are materially higher than on previous Claude models", and
  that mid-stream refusals are billed for the tokens produced before the block — which is exactly
  what seq 2079 shows: 1530 output tokens (reasoning, then the first character `直` at seq 2078),
  then the stop. Through the Converse API the Strands Bedrock provider maps that block to
  `content_filtered → 'contentFiltered'` (`node_modules/@strands-agents/sdk/dist/src/models/bedrock.js:60`,
  `STOP_REASON_MAP`), whereas the direct Anthropic provider yields `'refusal'`
  (`models/anthropic.js:595`). Darwin's refusal module — present in 0.0.34, added by commit
  `279f864` on 2026-09-04 — recognises only the Anthropic string:
  `REFUSAL_STOP_REASON = 'refusal'` in `src/agent/refusal.ts:14`, consulted by the TUI at
  `src/tui/App.tsx:1049` (`isRefusalStop(event.result.stopReason)` → `REFUSAL_NOTICE`), by both
  headless drivers (`src/headless.ts:280`, `src/headless-protocol.ts:478`) and by the child tools
  (`src/agents/subagent-tool.ts:311`, `src/agents/workflow-tool.ts:359`). None of them matches
  `contentFiltered`, so the SDK's normal end of turn (`agent.js:1136–1160`: a non-`toolUse` stop
  appends the message and returns the `AgentResult`) produced a turn that looked finished with no
  answer and no explanation. The transcript the user saw is what `trajectory replay` prints for
  seq 2076–2091: `you> 用户A是否有可能访问到用户B的文件？` / `darwin> 直` / `you> 什么？` /
  `you> 用户A是否有可能访问到用户B的文件？` — nothing after the last two prompts and no marker on any
  of them. The user's `什么？` (seq 2082) is the direct consequence: a one-character answer with no
  reason given. Why the classifier fired is not in the record — the Converse response's restriction
  category is not surfaced by the SDK and the reasoning text is stripped by design — but a question
  about one tenant reaching another tenant's files, asked over 662 k tokens of multi-tenant
  isolation code, IAM policies, root-squash/`ClientRootAccess` notes and a path-guard, is squarely
  the "dual-use cybersecurity" category the model card names. No earlier turn shows the pattern:
  the 271 model calls before seq 2079 stopped only with `toolUse` (258) or `endTurn` (13).
- **Root-cause area:** other (driver outcome naming — the stop-reason vocabulary differs per
  provider and darwin hard-codes one provider's word).
- **Suggestion:** Make `src/agent/refusal.ts` recognise the refusal *class*, not one string: a
  fixed, exported set `REFUSAL_STOP_REASONS = ['refusal', 'contentFiltered', 'guardrailIntervened']`
  (the three SDK stop reasons that mean "the provider or its classifiers declined", per the
  Bedrock `STOP_REASON_MAP` and the Anthropic mapping), `isRefusalStop` tests membership, and the
  notice/error strings name the actual stop reason received (`stop_reason: contentFiltered`) so
  the user can tell a Bedrock classifier block from a configured Guardrail. Every existing caller
  (TUI notice, headless stderr line and empty-reply error, `CHILD_REFUSAL_ERROR` in both child
  tools) changes behaviour only through that predicate. In the same change, `formatReplay` prints
  one bounded line at the transcript position for a refusal-class turn (`darwin> (model declined
  this request — stop_reason: contentFiltered)`), so the record and `/export` stop showing a bare
  `直` — today the only place the stop reason is visible is the `stop contentFiltered` clause on
  the model-call lines at the end of the replay.

### F2 — A refused turn leaves its truncated assistant message in the conversation, the next prompts are refused faster, and `/rewind` cannot cut the refused exchange out

- **Evidence:** Each refused turn appended two messages (`turnEnded.dropped.messageAddedEvent: 2`
  at seq 2081, 2086, 2091) and the context grew 662,282 → 663,830 → 663,847 (seq 2079, 2084,
  2089), so after turn 10 the history ends in `assistant: [reasoning, "直"]` and after turn 11 in
  an assistant message with an empty reasoning block and no text. The refusals then came faster
  and earlier each time: 34.5 s / 1530 output tokens (seq 2079), 4.7 s / 6 tokens (seq 2084),
  3.5 s / 7 tokens (seq 2089) — and turn 11's prompt was not the security question at all but
  `什么？` (seq 2082). The reading most consistent with the record is that once the flagged exchange
  is in the history, the classifier decides on the conversation, not on the newest prompt, so
  repeating (seq 2087) or clarifying (seq 2082) cannot succeed; the alternative — a deterministic
  block of the same question — does not explain turn 11. Darwin offered no way out: the refusal
  notice (had it fired, F1) says only "rephrase it or start a new turn", and the `/rewind`
  catalogue records a prompt only when its turn ended `endTurn` (`src/agent/runtime.ts:1217`
  `completed = true` only for `endTurn`; `:1231` `if (completed && checkpointId !== undefined)
  appendRewindCheckpoint(...)`), so prompts 10, 11 and 12 were never catalogued. The only way to
  remove the poisoned tail was to rewind to prompt 9 — discarding turn 9's completed answer from
  the conversation as well — or `/clear` and lose 664 k tokens of working context.
- **Root-cause area:** context management.
- **Suggestion:** Two bounded changes riding on F1's predicate. (a) In `AgentRuntime.send`,
  catalogue the rewind checkpoint also when the turn ended with a refusal-class stop: the SDK
  loop *did* complete (user and assistant messages both appended, no dangling `toolUse`), so the
  snapshot taken before the prompt is a valid boundary — `completed` keeps meaning `endTurn` for
  memory sealing and terminal delivery, and a new `catalogued = completed || refused` gates only
  `appendRewindCheckpoint`; failed and cancelled turns stay uncatalogued. (b) Extend
  `REFUSAL_NOTICE` with the remedy the catalogue now makes possible: "the declined reply was kept
  in the conversation; `/rewind` to this prompt removes it before you rephrase". Never an automatic
  retry or an automatic message removal: a refusal is a provider safety decision, not a transient
  error, and the SDK owns the conversation.

### F3 — After a resume, turn numbers restart at 1 in the same trajectory file, so `turn N` is ambiguous for every reader

- **Evidence:** seq 1 is `turn: 1` (`userInput`, run 1) and seq 94 is again `turn: 1`
  (`userInput`, run 2, after `runStarted { resumed: true, restoredMessages: 34 }` at seq 93). The
  two turns are unrelated (a 2 m 50 s planning answer vs. a 77 m 46 s build), yet `trajectory
  replay` prints two `turn 1 spend:` lines, `--turn 1` cannot name one of them, and this
  reflection had to qualify every citation with a run number. The cause is
  `TrajectoryRecorder`'s `private turns = 0` counter (`src/trajectory/writer.ts:494`,
  incremented at `:537`), which starts fresh in every process even though the recorder appends to
  the existing file and already reads the file's tail to recover the last `seq`
  (`writer.ts:49`, `:874`).
- **Root-cause area:** other (trajectory record shape).
- **Suggestion:** When the recorder opens an existing file for a resumed session, seed `turns`
  from the highest `turn` value found in the same tail read that recovers `seq` (falling back to 0
  when the tail is unreadable, exactly as `seq` falls back today), so turn numbers are unique
  within one `trajectory.jsonl`. `runStarted` keeps `turn: 0`; `replay`, `--turn`, `fork`,
  `search`, the self-reflection locator and the resume recap need no change because they already
  read `turn` from the records. Acceptance: a resumed recording continues at the next turn
  number; a fresh file still starts at 1; a damaged tail degrades to today's behaviour.
