## 4. Improvement findings for darwin

### F1 — Same-message `fileEditor` writes to one file race and every one reports success

- **Evidence:** seq 122–128 (one assistant message: six `str_replace` on
  `/home/ubuntu/workspace/strands-darwin/src/config.ts` plus `pnpm typecheck`); seq 137–142
  (all six `status: "success"`, each with a `cat -n` snippet showing *its* change); seq 143
  (`Cannot find name 'ANTHROPIC_API_KEY_ENV'`, `Cannot find name 'resolveAnthropicBaseUrl'`);
  seq 149/168 (model diagnosis); seq 153, 172, 176, 180, 188 (re-apply, one per message);
  seq 193 (green). The SDK's vended `handleStrReplace`
  (`node_modules/@strands-agents/sdk/dist/src/vended-tools/file-editor/file-editor.js:425–440`)
  is `await sandbox.readText(filePath)` → `buildStrReplaceResult` → `await
  sandbox.writeText(filePath, newContent)` with no lock, and darwin keeps the SDK default
  `ConcurrentToolExecutor` by invariant (AGENTS.md "Never set `toolExecutor`"), so N same-path
  edits in one message each read the original and the last write wins. `insert` and `create`
  share the same read/write shape (lines 408–422, 455–458).
- **Root-cause area:** tool description / orchestration (tool execution semantics)
- **Suggestion:** serialize *mutating* `fileEditor` calls per resolved absolute path within one
  Agent — a darwin-side wrapper `Tool` installed through `agent.toolRegistry.addOrReplace`
  exactly as `CodeGraphPreflightTool` is (`src/mcp/codegraph-preflight.ts:66–90`), holding a
  per-path promise chain so `str_replace`/`insert`/`create` on the same path run in call
  order and each sees the previous result; `view` and other paths stay concurrent; children
  built by `buildRecipeChild` get the same wrapper; `toolExecutor` is never touched. With
  serialization, each result's snippet is truthful and rule 8 of the system prompt (below)
  becomes correct instead of harmful. A `spike/verify-file-editor-serial.ts` case issues N
  disjoint `str_replace` on one file through a real `Agent` with a fake model and asserts all
  N survive.

### F2 — The system prompt tells the model to do the thing that clobbers, and to verify in the same breath

- **Evidence:** `src/agent/system-prompt.ts:91–94`, rule 8: "several edits to the same file
  belong in consecutive calls of one message only when they touch non-overlapping regions".
  The model followed it verbatim at seq 122–127 (six non-overlapping regions of `config.ts`,
  one message) and lost four of the six. Rule 7 ("Batch independent reads") says nothing about
  a verification command depending on writes in the same message, and the model put `pnpm
  typecheck` (seq 128) beside the edits it was meant to check — under concurrent execution
  that result (seq 143) is a snapshot of whatever state tsc happened to read. After the
  clobber the model stopped using `fileEditor` for multi-hunk edits and wrote files through
  `python3 - <<'EOF'` / `cat >` (seq 201, 206, 219, 224; 102, 107) — six writes with no
  edit-diff row and no `fileEditor` record in the trajectory.
- **Root-cause area:** system prompt
- **Suggestion:** rewrite rule 8 to state the real execution contract — until F1 lands: "tool
  calls in one message run concurrently; put edits to the same file in one call or in
  successive messages, never side by side, and never batch a verification command (typecheck,
  test, `rg` of the new text) with the edits it verifies"; after F1: "same-file edits in one
  message are applied in order; still send the verification in the next message". Add one
  sentence that file mutations go through `fileEditor` rather than shell heredocs or inline
  Python, so the edit diff, the permission classification and the `fileEditor` trajectory
  record exist. Keep the base prompt's byte budget in mind (`MAX_INSTRUCTIONS_BYTES` applies to
  AGENTS.md, not the base prompt, but the cache point sits after it).
