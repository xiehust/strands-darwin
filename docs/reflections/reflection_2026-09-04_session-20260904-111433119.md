## 4. Improvement findings for darwin

### F1 — Offloaded `json` tool results cannot be searched or sliced by the retrieval tool

- **Evidence:** seq 31, 35, 252, 391, 404 (five of six retrievals). Darwin's `bash` returns one
  `json` block `{cwd, error, exitCode, output}`; the SDK offloader stores it as
  `JSON.stringify(block.json, null, 2)`, so a 10 KB command output becomes one escaped-`\n` JSON
  line and the stored text has "6 lines". `line_range` starting past line 6 errors, `^`-anchored
  `pattern`s match nothing, and an unanchored pattern returns the entire line (seq 391). Each
  miss cost a model round (~130–180 K prompt tokens) and a disk re-read (seq 39, 256, 408).
- **Root-cause area:** context management (tool result shape × offloader storage/retrieval).
- **Suggestion:** in the pinned SDK patch (which already modifies
  `vended-plugins/context-offloader/plugin.js`), give `retrieve_offloaded_content` a line-preserving
  text projection for `application/json` references: when the stored JSON is an object whose
  string fields contain newlines, `pattern`/`line_range`/`context_lines` search a pretty view in
  which those strings are expanded onto real lines (e.g. `output:` followed by the output lines
  verbatim); the full-retrieval path (no pattern/range) returns the parsed JSON exactly as today.
  Preview text and stored bytes are unchanged, so restored-history repair and marker checks stay
  valid. Prove with `spike/verify-context-offload.ts`: an offloaded bash result with a 300-line
  output answers `line_range {100,120}` with those 21 output lines and `pattern '^## '` with the
  heading lines.

### F2 — `verify-skills.ts` pins the total backlog record count, so every legitimate append turns the gate red

- **Evidence:** seq 284/288 `FAIL all 86 production records pass paged-backlog validation` right
  after the research run appended SER-066/067; the Host stashed, confirmed the clean tree was
  green, and edited the literal to 88 inside the docs commit (seq 292–298, `5fb8eac`). The
  commit `43caa8c` that set 86 records the same drift ("b51c459 missed it"). This reflection's
  own accepted sections below make the current literal (88) wrong again, and fixing it is
  outside a reflection's mutation scope. The suite already asserts, per page, that parsed
  records equal `BACKLOG_DIRECTION_HEADING_PATTERN` matches, so the literal guards nothing
  additional.
- **Root-cause area:** other (test design / self-evolution workflow friction).
- **Suggestion:** replace `=== 88` in `spike/verify-skills.ts` with an independently derived
  total — the sum of `^## (SER|SRF)-\d{3} — ` headings across all routed pages, asserted equal
  to the parsed record count and `> 0` — keep the `SER-023` exception map, and drop the
  hard-coded number from the assertion label. `pnpm test` then stays green across research and
  reflection appends while still failing when a section fails to parse.

### F3 — `load_skill` bodies are offloaded like any tool result, so a skill costs two rounds and is read through a 1,000-token preview first

- **Evidence:** seq 308 `load_skill developer` → `[Offloaded: 1 blocks, ~6,677 tokens]`; the Host
  immediately retrieved the whole reference (seq 312, 8,110 characters in the record, `trunc`
  noted). The preview and the full body both remain in context, so the offload saved nothing and
  spent one model call; a model that trusted the preview would follow a truncated skill.
- **Root-cause area:** context management / system prompt (skill activation contract).
- **Suggestion:** exempt `load_skill` results from offloading. The SDK plugin's
  `_handleToolResult` already skips delegation and retrieval tools by identity; add a bounded
  darwin-owned exclusion (a small `excludeTools: string[]` option in the pinned patch, or the
  same by-name check) and pass `['load_skill']` from `src/agent/runtime.ts`. Skills are whole-read
  instructions (the `skills/` load-bearing rows), so the exclusion is a policy statement, not a
  size loophole; keep the 200-entry preflight and size caps on the skill side. Assert in
  `spike/verify-context-offload.ts` that a >2,500-token `load_skill` result reaches the model
  intact while a same-size `bash` result is still offloaded.

### F4 — Supervising a long child pays a full-context model round every five minutes just to wait again

- **Evidence:** ten terminal-focused `wait` calls returned `reason: timeout` at the 300 s cap

- **Root-cause area:** token spend / execution time (tool contract bound).
- **Suggestion:** raise `TERMINAL_FOCUSED_WAIT_MAX_MS` in `src/tools/background-wait-contract.ts`

  cap and the shared cursor behave exactly as now, and the still-running-timeout guidance stays.
  Update the schema `max`, the tool description, the `/tasks`/presentation text if it names the
  bound, the load-bearing paragraph ("finite 1–300000 ms") and the AGENTS.md row ("up to five
  minutes"); extend `spike/verify-background-bash.ts` with the new bound and a cancel during a
  long wait.
